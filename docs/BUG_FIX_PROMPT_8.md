### BUG-129 — `control_lock` never passes `confirmed` to `do()` → permanently blocked

| Field | Value |
|-------|-------|
| File | `apex_brain/tools/lock.py:114-118` |
| Severity | CRITICAL |
| Trigger | Any `control_lock()` call |

**Problem:** `control_lock()` delegates to `do("lock", service, {"entity_id": entity_id})` but never includes `"confirmed": True` in the `data` parameter. The generic `do()` function (generic.py:637-657) checks `data and data.get("confirmed")` and blocks all calls to PROTECTED_DOMAINS (which includes `"lock"`) without it. Since `control_lock` passes `data=None` (no fourth argument), every call returns the "CONFIRMATION REQUIRED" prompt — but there is no code path in `control_lock` to re-call with confirmation. The tool is permanently non-functional as a wrapper.

**Root cause:** When `control_lock` was converted to delegate to `do()`, the `confirmed` flag was not added. The deprecated wrapper has no mechanism to retry with confirmation.

**Fix:**
```python
# lock.py:114-118 — pass confirmed=True since control_lock is the tool itself
return await do(
    "lock",
    service,
    {"entity_id": entity_id},
    {"confirmed": True},  # <-- add this
)
```

**Regression test:** Call `control_lock(entity_id="lock.front_door", action="unlock")` and assert the return value does NOT contain "CONFIRMATION REQUIRED". Mock `do()` and verify `data` includes `{"confirmed": True}`.

### BUG-132 — `fact_extractor` uses `str.format()` with user content → KeyError on braces

| Field | Value |
|-------|-------|
| File | `apex_brain/memory/fact_extractor.py:89` |
| Severity | HIGH |
| Trigger | User message contains `{` or `}` (e.g., "use pattern {name}", JSON snippets, code, regex) |

**Problem:** `EXTRACTION_PROMPT.format(conversation=convo_text)` at line 89 substitutes the `{conversation}` placeholder. If `convo_text` itself contains unescaped single braces — e.g., a user saying "my regex is `{.*}`" or "set to `{value}`" — Python's `str.format()` interprets those as format placeholders and raises `KeyError` or `ValueError`. The outer `except Exception` at line 199 catches this and returns `[]`, silently dropping ALL fact extraction for that conversation.

**Root cause:** `str.format()` is unsafe when the template includes user-controlled text.

**Fix:** Replace `str.format()` with simple string concatenation or `str.replace()`:
```python
# fact_extractor.py:89 — replace .format() with safe substitution
prompt = EXTRACTION_PROMPT.replace("{conversation}", convo_text)
# Also change the EXTRACTION_PROMPT template to NOT use double-braces
# for the JSON examples, OR keep the double-braces and use:
prompt = EXTRACTION_PROMPT.replace(
    "{conversation}", convo_text
)
```

Wait — the double braces `{{` in the JSON examples (lines 43-47) are currently correct for `str.format()` (they escape to literal `{`). If switching to `.replace()`, those `{{` pairs would appear literally in the output. The cleanest fix:

```python
# Option A: Use a different placeholder that can't conflict
EXTRACTION_PROMPT = """...__CONVERSATION__..."""
# Then:
prompt = EXTRACTION_PROMPT.replace("__CONVERSATION__", convo_text)

# Option B: Keep .format() but escape user content
safe_text = convo_text.replace("{", "{{").replace("}", "}}")
prompt = EXTRACTION_PROMPT.format(conversation=safe_text)
```

**Regression test:** Pass conversation turns containing `{braces}`, `{0}`, `{}`, and `{key}` to `extract_from_conversation()`. Assert no exception and that extraction proceeds (even if no facts are found, it should not crash).

### BUG-133 — MCP bridge `execute_tool` doesn't reset `_connected` on failure → silent infinite failures

| Field | Value |
|-------|-------|
| File | `apex_brain/tools/mcp_bridge.py:195-221` |
| Severity | HIGH |

On subsequent calls, `execute_tool()` checks `self._connected` at line 204 and sees `True`, so it attempts `self._session.call_tool()` again — which will also fail because the session/transport is dead. except Exception as e:

    return f"MCP tool error ({name}): {e}"
```

Additionally, consider adding a `reconnect()` method or auto-reconnect in `execute_tool` when `_connected` becomes False.

**Regression test:** Connect MCP bridge, simulate a `call_tool` failure (mock session to raise). Assert `_connected` becomes `False` after the error. Assert subsequent calls return the "not connected" message immediately.

If the handler raises (e.g., network error during `_handle_backup_create`, timeout during `_handle_restart_core`), the exception propagates past the audit log at lines 492-501.             user_approved=tier > 0,

```

**Regression test:** Mock a handler to raise `RuntimeError`. Call `manage()` and assert the audit store received a log entry with `result` starting with `"error:"`. Assert the returned string contains the error message.

### BUG-137 — Semantic dedup discards new fact's key in favor of stale match

| Field | Value |
|-------|-------|
| File | `apex_brain/memory/knowledge_store.py:265-277` |
| Severity | MEDIUM |
| Trigger | Storing a new fact whose value is semantically similar to an existing fact with a different key |

**Problem:** When `_check_duplicate()` finds a semantic match (similarity ≥ 0.92), the code at lines 270-277 just touches the existing fact's timestamp — it does NOT update the existing fact's key, value, or confidence. This means:
- Existing: `key="coffee preference"`, `value="likes espresso"`
- New: `key="morning drink"`, `value="prefers espresso shots"`, `confidence=0.95`
- Result: The new fact's more specific key ("morning drink") and updated value are silently discarded. Only the old fact's `last_mentioned_at` is bumped.

This makes semantic dedup too aggressive — it throws away newer, potentially better-worded facts.

**Fix:**
```python
# knowledge_store.py:270-277 — update key/value if new confidence >= existing
if dup_id is not None:
    # Fetch existing confidence
    dup_cursor = await self._db.execute(
        "SELECT confidence FROM facts WHERE id = ?", (dup_id,)
    )
    dup_row = await dup_cursor.fetchone()
    old_conf = dup_row[0] if dup_row else 0
    if confidence >= old_conf:
        await self._db.execute(
            "UPDATE facts SET key = ?, value = ?, confidence = ?, "
            "embedding = ?, last_mentioned_at = ?, updated_at = ? "
            "WHERE id = ?",
            (key, value, confidence, embedding_blob, now, now, dup_id),
        )
    else:
        await self._db.execute(
            "UPDATE facts SET last_mentioned_at = ?, updated_at = ? "
            "WHERE id = ?",
            (now, now, dup_id),
        )
    await self._db.commit()
    return dup_id
```

**Regression test:** Store fact A with low confidence. Store semantically similar fact B with higher confidence and different key. Assert fact B's key and value replaced fact A's.

### BUG-142 — `conversation_store` has no pruning mechanism → unbounded DB growth

| Field | Value |
|-------|-------|
| File | `apex_brain/memory/conversation_store.py` (entire module) |
| Severity | LOW |
| Trigger | Long-running deployment (weeks/months of continuous use) |

**Problem:** Every conversation turn is stored permanently via `save_turn()` and there is no mechanism to prune old entries. Unlike `knowledge_store` which has `cleanup_expired()` and `decay_confidence()`, the conversation store grows without bound. Over months of use, the SQLite database could grow to hundreds of MB, slowing queries and consuming disk space on embedded devices (Home Assistant often runs on RPis or NUCs with limited storage).

**Fix:** Add a `prune()` method:
```python
async def prune(self, keep_days: int = 90) -> int:
    """Delete conversation turns older than keep_days."""
    from datetime import timedelta
    cutoff = (
        datetime.now(timezone.utc) - timedelta(days=keep_days)
    ).isoformat()
    cursor = await self._db.execute(
        "DELETE FROM conversations WHERE timestamp < ?",
        (cutoff,),
    )
    await self._db.commit()
    return cursor.rowcount
```

Call this from the scheduler's daily maintenance cycle.

**Regression test:** Insert turns with old timestamps. Call `prune(keep_days=1)`. Assert old turns are deleted and recent ones remain.
